# Windows 真实素材目录测试

2026-10-23 更新。当前只联调 Windows，不制作安装包；规则敲定后再接安卓，最后打包发布。

## 当前操作

在项目目录启动调试版：

```powershell
& 'D:\tools\flutter\bin\flutter.bat' run -d windows
```

启动后默认进入 **开始测试**，点击素材目录右侧文件夹按钮，选择：

```text
D:/文档/鹏城项目/13专项-沉浸式/项目测试/13主观测试
```

选的是四个 *_renders 文件夹共同的上级目录，软件自动读取；也可以粘贴路径后点“读取目录”。同页填写每个序列的抽样数量，设置 Patch 和 3D，核对“本次测试参数”后点“登记参与者并开始测试”。无需先运行脚本、复制原图或手动发布版本。每位参与者登记不同编号。

中断后返回此页，下方列出不同参数下的未完成会话，可直接恢复。新单页流程与验证见 [Windows 单页开始测试](windows-start-test.md)。旧的草稿、导入和发布入口移到“高级实验管理”。

以前导入的“真实素材 · 真实感流程演练”采用单帧加全部相机，仅作为历史演练保留。请使用新加载的 **真实素材 · 每人随机帧与视点**；旧 source 和旧会话不会被改写，也不是当前抽样方案。

## 原目录与抽样

```text
<sequence>_renders/
  frame000000/
    test/primitive/
      gt/00000.png
      renders/00000.png
      per_view_count.json
```

| 序列 | 帧数 | 可用视点 | 候选图片对 | 每人抽取 |
| --- | ---: | --- | ---: | ---: |
| VRU_gz | 250 | 0、10、20、30 | 1,000 | 4 |
| VRU_dg4 | 250 | 0、10、20、30 | 1,000 | 4 |
| Dance_Dunhuang_Pair_1080 | 250 | 0、10、20、30、40、50 | 1,500 | 6 |
| Show_Groups_4K | 250 | 0、10、20、30、40、50 | 1,500 | 6 |

完整素材池共 5,000 对、10,000 张图片，约 17.98 GiB。每位参与者独立从各序列的全部“帧 × 视点”组合中均匀、不放回抽取。所有帧都具备相同视点集合，故组合均匀抽样等价于随机帧加随机视点，不再先锁定一帧、然后遍历相机。不强求一位参与者覆盖每个相机；同一图片对不会在抽样阶段重复抽中。

用户已确认文件 00000、00001 等按导出顺序对应表中的相机号。每个序列只允许本次使用的一套 renders 目录；缺失任一 GT/render 配对或某帧视点不完整时报告错误，不静默跳过。

每人抽取 20 对，每对按两种先后次序各呈现一次，共 40 次判断。四个分组和组内题次独立随机，重复题不相邻。正式呈现仍为提示 2 秒、图片 3 秒，答题不限时。

会话保存随机种子、排程版本、实际题目列表及每题 frame/view；两轮使用同一批抽中的图片。恢复时重放当前未答题，不重新抽样。不同参与者使用新种子，通常抽到不同图片；偶然选中同一图片是正常的。

## 软件包与素材分离

新发布的 v2 实验包只含 study.json 和 release.json，保存规则、相对图片路径与素材清单。物理素材目录位置记录在本机 materials.json，不进入包，也不进入结果定义。

原图始终从已选择的素材目录读取。移动目录后，使用“加载 / 更换测试素材目录”重新定位。导入实验包后，同样先加载完整素材目录，才能开始采集；素材总量不受旧 ZIP 的 1 GiB 展开上限约束。旧版自带图片的包继续兼容。

直接索引只读取目录和文件大小，不在加载时解码或计算全部 18 GiB 图片的哈希。每次登记参与者，才完整解码其抽中的图片、核对尺寸并保存 SHA-256；呈现和恢复时再次核对会话指纹。已在本机其他会话使用过的同一路径图片若变化，拒绝继续；合并结果时，同一路径出现冲突指纹也拒绝合并。未抽中的图片没有全量像素校验，目录加载不表示整池所有图片都已验证。

Windows 当前直接读取文件系统；Android 持久目录授权及整目录读取留到下一阶段联调，本轮不构建或发布 APK。

## 验证与记录

[原生测试](../integration_test/random_pool_test.dart) 直接读取用户提供的根目录，验证：

- 完整 5,000 对素材池与两位参与者不同的随机帧/视点样本。
- 第一位参与者 40 次作答、答完两题后保存并重新加载，恢复的题目和指纹完全一致。
- 原图不复制入软件，导出的元数据包重新导入后必须单独加载素材目录。
- JSON / CSV 导出、跨仓库结果合并和重复导入幂等。
- 每题 frame、view、sampling_seed、图片指纹保留在结果中。

测试答案明确标为模拟，完整流程回归使用 30 ms 的测试专用呈现时长；生产时长未改变。先前历史单帧演练曾单独检查 2 秒 / 3 秒实际应用计时，不能将该次旧抽样结果当作新方案的真人主观评价结果。

证据保存在 validation/random-pool-windows/，模拟结果的实际目录记录在 report.json 中。测试数据和原图不提交 Git。

素材池初次回归结果：静态分析无问题，45 项 Flutter 测试、20 项 Python 测试通过；Windows 原生整轮约 43 秒（测试专用加速计时），目录索引与发布约 2,196 ms。两位模拟参与者各抽中 20 对并冻结 40 张图片指纹，第一位完成 40 次作答；软件仓库额外复制的原图数为 0。第一位的 VRU_gz 样本为 (帧164, 视点20)、(帧178, 视点0)、(帧46, 视点20)、(帧201, 视点0)，第二位对应样本不同，验证了不再限制为单帧或遍历相机。

双眼 SBS 与可选 Patch 的后续实现、操作和最新验证见 [双眼与 Patch](stereo-and-patch.md)。原目录可直接用于 2D Patch；双眼模式需明确左右眼文件关系，不能将相邻相机自动当成一对眼睛。

## 正式实验状态

当前仍是演练环境：尚缺 3～5 对独立练习题、2 对控制题，自动载入版本明确设为 isDemo=true，不产生正式真实感通过结论。软件流程跑顺后再确认完整正式方案，安卓联调和安装包发布都在之后进行。

旧真实感 profile 1 的固定题库与逐图人数条件保留复算。新模板使用 profile 2 和每人抽样配置，按序列统计；其人数、专家比例与阈值属于实验配置，不代表自动满足某一外部认证规范。
